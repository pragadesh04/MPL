# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**MPL — Mini Militia Premier League.** A web app that runs Mini Militia tournaments:
organiser setup → captains and soldiers register → live player auction on phones →
leftover auto-allocation → groups + knockout generated from the team count → results and champion.
Several organisers can run tournaments at the same time.

The full product spec, business rules, data model, endpoints and UI screens are in
**[PLAN.md](PLAN.md)**. Read the relevant section before building a feature.
PLAN.md §11 is the decisions log; don't re-open decided questions. PLAN.md §12 describes the
earlier reference build (mpl-auction-blush.vercel.app), which sets the look and auction feel.

> **Status: Phase 0 (Foundation, PLAN §13.3) is done and tagged `foundation`.** The shared
> scaffold, schema, contracts, rule signatures, auth, roles, real-time base, design base and
> seed exist; lane features (§13.4–13.6) are next. Not yet deployed: no Vercel project, Neon
> database or Ably key has been connected (local dev runs on PGlite with real-time recorded).

## Stack

**One full-stack Next.js app on Vercel, with no separate backend and no long-running server.**
TypeScript strict, Next.js 16 App Router + React 19, Tailwind 4 + shadcn/ui, React Hook Form +
Zod, Zustand (live auction state only), Framer Motion.

- **Database: Neon PostgreSQL via Drizzle ORM.** Schema in `src/server/db/schema.ts`; SQL
  migrations generated by `drizzle-kit` into `drizzle/` and committed. Use the Neon serverless
  **Pool** (WebSocket) for transactions and the HTTP driver for one-shot reads.
- **Real-time: Ably.** The server publishes after commit with the Ably REST SDK. Browsers only
  **subscribe**, using tokens from `POST /api/realtime/token`. **Clients never publish**; every
  action is an HTTP request.
- **Webhooks: outgoing only** (Discord + generic HMAC-signed), sent with `after()` so they never
  slow down a bid. Browsers get events from Ably, not webhooks.
- Reads happen in **Server Components**; writes go through **Server Actions** (forms) or
  **Route Handlers** (`src/app/api/**`: auction API, token/code endpoints, CSV upload, webhooks
  admin, matches API). Both are thin wrappers: **all logic and authorisation live in
  `src/server/services`**.
- `src/server/**` is server-only (`import 'server-only'`); never import it from a Client
  Component. Route Handlers and actions run on the **Node.js runtime, never Edge** (argon2 and the
  Neon Pool need Node).
- `proxy.ts` (Next 16's renamed middleware) only redirects when there's no session cookie.
  It is **not** an authorisation layer.

Layout and the full route map are in PLAN.md §8.

## Architecture rules that span files

- **Rules live in `src/lib/rules` as pure functions** (`nextValidBid`, `canTeamBid`,
  `allocateLeftovers`, `validateReadyToStart`, `generateGroups`, `generateRoundRobin`,
  `computeStandings`, `seedKnockout`, `generateBracket`, `assignMatchOrder`,
  `buildTournamentTree`). Services enforce them; the UI calls the same functions only to
  disable buttons and explain why. Never re-implement a rule inline in a component or route.
- **The database is the source of truth and Postgres `now()` is the only clock.** Every
  response and event carries `serverNow`; clients only draw countdowns from it.
- **Bids:** one transaction that runs `SELECT … FROM auction_state … FOR UPDATE`, then
  `settleDue`, then checks `expectedVersion` (409 = outbid), `canTeamBid` and the amount, then
  `UPDATE auction_state` (`version + 1`) and `INSERT INTO bids`. Keep these transactions tiny,
  with no network calls inside.
- **No server timers.** `settleDue(tournamentId)` applies every time-based step that is due
  (lot expiry → sold/unsold, break expiry → next soldier). It runs inside the locked transaction
  on every auction read/write and on `POST /auction/tick`, which every connected client calls when
  a countdown hits 0. Exactly one caller wins; the rest are no-ops.
- **Publish to Ably and send webhooks only after COMMIT.** Two sequences are used:
  `auction_state.version` for `t:<id>:auction` and `tournaments.roster_version` for
  `t:<id>:updates`. Clients apply an event only if it is `local + 1`; on a gap they refetch the
  snapshot (`GET /auction`), and they also refetch on reconnect and after 10 s of silence
  during a live lot.
- **Auction commands carry a `commandId`**, stored in `processed_commands`, so retries and
  double-taps are idempotent.
- **Sale, undo, release, assign, allocation and reset each run in one transaction** (purse,
  soldier, state and audit log together).
- **Settings lock at Start Tournament**, and soldier registration closes. Afterwards only the
  timer, break and `unsoldPolicy` stay editable; any other change is a logged admin override.
- **Money is integer Militia Points (MP).** `integer` columns, no floats; the database
  `CHECK (purse_remaining BETWEEN 0 AND purse_total)` is the last line of defence.
- **Let the database enforce invariants**, for example one active tournament per owner
  (`UNIQUE (owner_id) WHERE status NOT IN ('COMPLETED','CANCELLED')`), unique team
  name/colour, one record per user per tournament, and unique `match_number`. Map
  unique-violation errors to 409s instead of pre-checking in code.
- **Rate limiting is Postgres-backed** (`rate_limits` table); in-memory limits don't work across
  serverless instances.
- Tests: services run on PGlite, but **race and concurrency tests need real Postgres** because
  PGlite is a single connection.

## Identity & access (details in PLAN.md §2, §5)

- **One `users` table for everyone** (username + argon2 password; organisers also give an
  email). The JWT in an httpOnly cookie holds **only `userId`**. There is **no "current
  tournament" in the session.**
- **Roles are per tournament** and resolved on every request by
  `loadTournamentRole(userId, tournamentId)` from three sources: `memberships` (OWNER /
  CO_ADMIN / AUCTIONEER), `leaders.user_id` (captain) and `players.user_id` (soldier).
  `requireRole(...)` checks the result against the permission table in PLAN.md §2.4; no role
  means 404. Every tournament route has `:tournamentId` in its path. The Ably token endpoint
  runs the same check and grants subscribe-only access to that user's tournament channels.
- **UI terminology: leaders are "Captains" and players are "Soldiers".** Code, tables and API
  paths use `leader` / `player`. Keep this mapping and don't rename either side. Soldiers have
  no tiers or categories, only a base price.
- **Separate tables** `leaders` and `players`, each with a nullable `user_id`. One captain =
  one team; `teamCount` is derived, never input. Purse columns live on `leaders`. A user can't
  be both captain and soldier in one tournament; this is checked in a transaction that locks the
  tournament row. Name, IGN and photo are **snapshotted** at join time.
- **Multi-tenant (PLAN.md §2.0):** unrelated organisers each have their own captains and
  soldiers, scoped through their own tournament. **No endpoint lists or searches users.** The
  only cross-organiser read is the exact Player ID lookup, which returns the public card only
  (photo, display name, IGN). Every service gets a tenant-isolation test (an organiser from A on
  B's tournament → 404).
- **Three ways to join an organiser's tournament (PLAN.md §2.3), all ending in a `leaders` or
  `players` row:**
  - **A. Personal link** `/i/<token>`, for captains **and** soldiers. The token is the AES-256-GCM
    encryption of `{ k: 'L'|'P', id, tid, v }` with `INVITE_LINK_SECRET`; `v` must equal
    `link_version`. It is claimed once and pre-approved.
  - **B. Organiser key:** one stable 6-character key per organiser (`users.organiser_key`, shown
    `XXX-XXX`) that resolves to their **current active tournament**. The player picks captain or
    soldier at sign-up and arrives `PENDING`; the organiser approves (purse / base price),
    switches the role, or rejects.
  - **C. Player ID request:** every player has a public `player_code` (`#XXXXXX`). The organiser sends
    a `join_requests` row with role and purse/price; the player accepts (joins pre-approved) or
    declines (optionally blocking that organiser).
- **Free agents:** signing up with no key gives a player account under **no** organiser, until
  path A, B or C.
- Only **approved** rows count as tournament roles. Start is blocked while anyone is pending,
  and Start expires pending requests in the same transaction. Live inbox events go on the
  Ably channel `u:<userId>`.
- Organiser invites and password resets are hashed, single-use, expiring tokens. There's **no
  email service**: everything is a share-link. Organisers issue reset links only for participants
  of their own tournaments; a co-admin can never reset an owner's password. Invalid tokens or codes
  return the same generic 404.
- Only one organiser controls the auction console at a time
  (`auction_state.controller_user_id`; "Take control" is logged).

## Domain rules (details in PLAN.md §3–4)

- A bid is valid only if: the lot is live and not expired, `amount >= nextValidBid` (exactly
  equal when `allowCustomBids` is off), the team isn't already leading, `squadSize <
  maxPlayersPerTeam`, `amount ≤ purseRemaining`, and the bidder is that team's captain (or the
  controlling auctioneer making a logged fallback bid). There is **no** purse reserve.
- Defaults follow the reference build: 50 MP purse, opening bid 1, +1 raise, 60 s clock that
  every bid restarts, 2 s break, then the next soldier opens automatically in random order.
- **When nobody bids** (`unsoldPolicy`): default `REAUCTION_THEN_ALLOCATE`, meaning re-auction rounds
  at `reauctionPricePercent`, then **leftover allocation**: unsold soldiers (highest base price
  first) go at price 0 to the team with the **fewest players** below max (tie-break: lowest MP left,
  then team order). The alternatives are `RANDOM_SQUAD` and `ADMIN_DECIDES`.
- **Start is blocked unless** every captain has linked an account and finished team setup, no
  soldiers are pending, `captains × (min − 1) ≤ approvedSoldiers ≤ captains × (max − 1)` (the
  captain always fills one slot and is never auctioned), team names and colours are unique, and
  every base price is ≥ `minBasePrice`.
- **Format: groups, then knockout.** Standings are always **computed from match results, never
  stored**. Tied games can't be saved; they are replayed. 2 teams → final only; 3–5 teams → one group.
- **Match order:** every non-bye match has a `match_number` (`assignMatchOrder`). Organisers
  reorder unplayed matches **within a stage only**. The **List** and **Tree** views
  (`/t/[id]/matches`) come from the same `matches` rows and are visible to **every participant
  role** (404 for anyone else).
- **Team colour is never the only identifier.** Always show the name or short code next to it.
  Use Tailwind theme tokens (lime, amber, gold, blood, sand, muted) from the reference look, not hex.

## Gotchas found while building Phase 0

- **Next 16 Cache Components is OFF** (`cacheComponents: false` in `next.config.ts`). Pages read
  the session / database at request time; with it on, every such read outside `<Suspense>` is a
  build error. Don't turn it on without a plan for every page. Never add `export const runtime`.
- **Bundled Next docs win over memory:** `node_modules/next/dist/docs/` describes this exact
  version (see `AGENTS.md`). Middleware is `src/proxy.ts`; `LayoutProps` / `PageProps` are
  global types generated by `next typegen` (run by `npm run type-check`).
- **Shared rule signatures:** `src/lib/rules/index.ts` re-exports one module per rule. The owning
  lane replaces the `NotImplementedError` body in its module; signatures used by another lane
  (e.g. `planFormat` in Lane A's Rules step) change only through an integration note.
- **Cross-lane stubs:** `initializeAuction(tx, tournamentId)` (stub creates an empty
  `auction_state`) and `startGroupDraw(tx, tournamentId)` (stub throws 501).
- **PGlite is one connection per directory:** stop `next dev` before `npm run db:seed` /
  `db:migrate` on the local PGlite dir, and on Windows make sure the `next dev` child process is
  really gone (it can keep the port and the directory locked after the parent is stopped).
- **`server-only` throws outside Next.** Vitest aliases it to an empty module; tsx scripts must
  not import modules that import it (scripts use `connect.ts`, `migrate.ts`, `env-core.ts`).
- **Raw SQL results differ by driver;** use `rows<T>()` from `src/server/db/sql.ts`, not
  `db.execute()` directly.
- **Schema invariants beyond PLAN §5** (documented there too): one OWNER membership per
  tournament; `players.team_id` set exactly for SOLD / ALLOCATED; tied `match_games` rejected;
  unique team short code; `group_teams.tournament_id` keeps a team in one group; `matches.stage =
  'GROUP'` exactly when `group_id` is set. Insert the owner's `memberships` row together with the
  tournament (see `makeTournament` in `src/test/factories.ts`).
- **The `useTestDb` name trips the React hooks lint rule;** the helper is `setupTestDb()`.
- **Pages that query the database without reading cookies get prerendered at build time.** Call
  `await connection()` (from `next/server`) first, as `src/app/dev/page.tsx` does, or the build
  will query (and bake in) whatever database it can reach.
